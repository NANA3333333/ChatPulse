# 私聊事件记录与讨论状态设计建议

状态：设计稿，尚未实施。依据：用户提供的 `C:/Users/Nana/Desktop/implementation_plan.md`、现有代码与此前实际对话诊断。

## 目标

保留可以再次使用的事实记忆，同时记录一次讨论进行到了哪里、哪些话已经说过、用户是否愿意继续。防止已搁置的争执在无关话题里被自动重启；允许真实追问、新进展、纠正和约定提醒得到正常回应。

## 对原稿的调整

保留“话题状态”和“已表达立场”的思路，但不直接将所有讨论过的话题设为禁止重开。

- 最近五轮提到过，不能单独成为禁提依据；用户可能在深入讨论同一个问题。
- 连续讨论四轮不能单独成为过时或应换话题的依据。更有用的信号是连续输出同一结论、用户没有提出新问题、也没有新增事实。
- 用户明确结束讨论可以立即生效，不必先满足三轮重复。
- “算了”必须结合指向理解。例如“算了，我自己去医院”结束的是求助方式，不能据此认定健康事件已解决。
- 换话题通常意味着把前一话题搁置，不能推断双方达成共识。
- 角色仍然有情绪，不意味着用户欠它一个解释或这场争执必须继续。

原稿的两个技术前提需要校准：

1. `server/engine.js` 当前重复输出拦截条件为 `isDuplicate && !isUserReply`，不覆盖正常回应用户的私聊；现有文本级防重复不能视为已完整解决。
2. 当前 `updateConversationDigest` 返回最多三段 `private_context_summaries`，对滑动窗口之外、达到阈值的历史批次生成纯文本摘要。它并非每轮更新的结构化私聊状态。数据库仍有 `conversation_digest_cache` 表，但不能因此假定存在可直接读取的实时关闭清单。

## 一、区分三类记录

### A. 事件事实：发生了什么

保存具体事实、时间和来源消息，区分用户陈述、角色陈述、系统事实与未经确认的推测。纠正通过来源建立替代关系，不把角色推断反复写成用户的稳定属性。

例如：

- 原记录：角色推断用户正在租房。
- 新记录：用户说明住父母的房子，没有房租。
- 处理：旧推断已被用户纠正，当前使用新事实；单纯关闭“房租话题”无法消除事实错误。

真实事件是否完成，可另记 `unknown / pending / resolved`；只有有证据时才更新。不是每段聊天都需要生成持久事件。

### B. 讨论状态：这件事现在还聊不聊

| 状态 | 含义 | 默认回复行为 |
| --- | --- | --- |
| active | 本轮正在讨论 | 回应新增问题和信息 |
| parked | 暂时离开或搁置，可以仍有分歧 | 无关话题中不主动追问；用户回接时继续 |
| closed | 该次讨论已答复完成，或用户明确结束 | 保留结论；有明确追问、新进展或纠正时再打开 |

`closed` 不代表忘记、不代表意见一致、不代表事件完成，也不代表永久禁止谈论。

### C. 已表达内容与约定：哪些话说过，哪些事还要做

- 已表达立场可记一条中性的命题：“角色已提醒某个具体风险”。不反复注入完整说教，也不改写为“用户就是不听劝”。
- 同一立场没有新理由时，可以保留态度，不再重讲理由。
- 真实的待办、承诺和提醒单独保存；讨论关闭不自动取消约定。到期提醒或真实系统进展可以触发相关回应。
- “用户还没认错”“用户没接受角色的看法”不自动形成待办。

## 二、最小状态记录

第一版可使用每个角色一份小型结构化状态，只跟踪少数近期主题；不建设庞大的剧情系统。

```json
{
  "topic_id": "stable-local-id",
  "subject": "某次具体讨论的中性标题",
  "status": "parked",
  "outcome": "双方未达成一致，本轮已转向其他问题",
  "said_positions": ["角色已说明一个具体担忧"],
  "evidence_message_ids": [123, 127],
  "last_changed_turn_id": 127,
  "close_reason": "user_switched_topic"
}
```

要求：

- 主题要足够具体，例如“昨晚那次宠物互动的争论”；不要关闭“宠物”“关系”“工作”这种宽泛领域。
- 使用真实消息 ID 和完整对话轮标识，多气泡只算一轮。利用已有回复锚点识别新消息；旧记录只能保守分组，不能把所有相邻角色消息都武断合并。
- 沉默和时间流逝不作为“同意”或“解决”的证据；仅允许不活跃主题退出当前焦点。
- `close_reason` 与 `outcome` 描述可观察变化，不推断隐藏动机。
- 记录只基于当前可见、选中的对话版本。

## 三、何时关闭与重新打开

关闭或搁置的依据优先看最新用户输入及明确结果：

- “先不说这个”→ parked 或 closed，原因是用户停止讨论，不记录为达成共识。
- 用户明确转向新问题→旧主题 parked。
- 明确任务已完成、疑问已答复并得到承接→可 closed。
- 模型拿不准→不制造已解决结论；继续保守回应当前句。

重新打开的依据：

- 用户直接提及，也包括语境明确的代词与省略表达，例如“那刚才那件事，你后来怎么想的”。
- 同一事件出现真实的新进展、用户纠正或到期约定。
- 召回相似记忆、角色再次想起、负面情绪仍然存在，都不单独构成重新打开的依据。

## 四、接入现有辅助链

建议扩展现有 `runTopicSwitchGate`，在同一次请求中返回话题决定和小型状态增量，不另外串联话题提取、立场提取、关闭提取三个调用。

当前闸门使用严格单行格式与 `parseTopicSwitchDecision`，所以接入时需要一起修改输出契约、解析校验、缓存版本和失败恢复，不能只给现有 prompt 追加几个字段。

建议数据流：

1. 输入上一份状态、尚未处理的完整对话轮和最新用户消息。
2. 辅助模型提出主题变化、纠正、关闭及已表达内容的增量，附来源消息 ID。
3. 程序校验 ID 属于当前对话版本、状态转换合法、记录长度受限；不接受不存在的证据。
4. 下游检索规划与主模型共享同一份状态。保留记忆服务和记忆内容；规划器看到“已搁置”，才不会先把中性话题重新解释成旧冲突。
5. 新回复成功并进入当前选中版本后，才可把其中确实表达的内容用于下一轮状态更新。计划输出的内容不等于已经说出口。

状态扩展字段不可用时，保留上一次可靠状态，禁止凭空关闭；原有话题判断若仍有效，可以继续使用。避免因这个可选改进额外增加整条私聊的硬失败点。

这里省掉的是额外调用次数；已有请求仍会增加少量输入和输出 token，不能称为零成本。

## 五、注入主模型的提示示意

只呈现与本轮有关的少量中性状态，不再复制完整争执。以下是“喜恶同因”被用户澄清后的示意，并非对当前数据库状态的写入：

```text
[本轮讨论状态]
当前：交流“喜恶同因”这一观点。
已澄清：用户表示这段观点没有指向特定对象；此前关于影射关系的解释缺乏支持。
已搁置：先前的宠物互动争论。没有达成共识；当前未继续讨论。

[使用规则]
- 先回应当前讨论与最新用户输入。
- 已搁置或关闭的话题保留事实，不在无关回复中重新追问、说教或列举旧证据。
- 用户明确回接（包括语境清楚的省略表达）、带来新进展或纠正时，回应本次新增内容；用户要求完整回顾时可以展开。
- 角色可以保留情绪和立场，无需再次证明情绪理由。
- 关闭讨论不代表用户承认错误、接受建议或事件已经解决。
```

第一版限制为少量条目和几百字符，避免“关闭清单”本身再次放大旧话题。原始记录可在后台保存，主提示不需要全量展示。

## 六、与重 roll、编辑和删除的关系

- 重 roll 使用该轮已经保存的生成前状态与辅助结果，不重新调用状态提取模型。
- 未选中的候选回复不能成为新的既成事实或已表达立场。
- 切换、编辑或删除旧消息时，使依赖受影响消息及版本的派生状态失效；在下次正常对话中从可靠检查点增量重建。
- 用户明确说过的结束或纠正，不能仅因角色生成了另一个版本就被忽略。
- 回复生成失败、过期或被取消，不推进“角色已表达”的状态。
- 第一版只处理私聊；群聊与城市中的同名话题不能自动继承关闭状态。真实跨渠道事件要有明确来源关系。

## 七、实施顺序与验证

1. 先完善上述状态语义、来源和版本规则；明确结束、搁置、事实纠正与待办是不同概念。
2. 以现有话题闸门为入口实现最小状态增量，输出短小状态块，同时供检索规划与主回复使用。
3. 将最近完整回复的“已表达要点”接入状态，逐步替换长篇反重复原文引用；避免再堆叠一整套重复清单。
4. 最后根据对照结果调整提示词，不先通过提高采样惩罚或固定轮数强制转向。

关键验收场景：

- 换话题后不主动翻旧账，但事实仍能被需要时正确召回。
- 用户否认动机解读后，旧推断不能再作为事实推进。
- 同一话题连续讨论超过五轮，有新问题时仍正常回应。
- 用户说“算了，我自己处理”，停止原讨论但不虚构事情已解决。
- “没有租房”等事实纠正能覆盖旧推断。
- 用户通过代词回接、明确要求复盘时，可以正常重新讨论。
- 真实承诺与到期提醒不会因闲聊结束而丢失。
- 重 roll 不增加辅助调用，切换候选后状态只取当前版本。

先做状态转换与版本一致性的离线测试，再用少量有代表性的生成对照评价效果。提示词上的合理性不等于已经证明生成改善。
