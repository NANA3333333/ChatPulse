## 补充：以未来多人在线服务为目标

用户进一步明确：本次安全关注的重点是未来多个用户同时使用时的账号、密码及数据隔离。桌面分发问题属于旁支，不应作为后续工作的主线。

当前设计已具备多用户基础：认证资料集中在 master.db；业务资料按用户分别存入 SQLite；请求通过已验证会话确定 userId 后选择 req.db；Qdrant collection 名称也按 userId 划分（server/qdrant.js:25）；调度器连接相应用户业务库。

“每人一个数据库文件”降低了查询漏写 userId 条件的风险，但不等于完整权限隔离。所有库仍由同一个后端进程访问，文件服务、备份、向量检索、后台任务、WebSocket 和浏览器缓存都必须沿用同一用户身份。

本轮追加检查发现一处浏览器缓存边界：roomEditorCore.js:36 使用不带 userId 的 localStorage key 保存行为树；AuthContext.jsx:32 的退出清理只移除账号与 token；RoomAssetEditor.jsx:925 在服务端没有树时，会把本地已有生成节点的树写回当前登录账号。相同浏览器从 A 切换到 B 时存在把 A 的本地状态带入 B 的代码路径。该发现来自源码检查，尚未进行双账号浏览器端复现。它影响共享浏览器切换账号的场景，不代表不同电脑的 localStorage 会共享。

密码当前存储为 bcrypt 哈希，并有锁定与限流，不能描述为明文保存用户密码。模型 API key 则是需要再次调用时使用的凭据，目前作为业务字段存储，与登录密码的处理方式不同。对外托管时应考虑应用层加密、密钥独立管理，并避免在普通数据导出中默认携带可用凭据。脱敏返回不等于数据库中的值已加密。

围绕多人在线服务的优先顺序应为：

1. 固定账号身份与权限边界，去除基于可修改用户名自动授予 root 的逻辑。
2. 补齐备份/媒体、WS 会话、前端缓存的用户隔离。
3. 统一密码修改、会话撤销、令牌到期和登录防护；部署时使用 HTTPS，明确浏览器会话存储与 CSRF/XSS 防护方案。
4. 用两个隔离测试账号验证所有读取、更新、删除、导出、检索和订阅操作不能越权；测试注销、改密、封禁及同浏览器切号。
5. 再做并发和运维验证，包括每用户任务/存储/模型额度、数据库连接回收、备份恢复、迁移一致性。

SQLite 可以作为单节点试运行方案；“多人”本身并不要求立即换数据库。若确定要多实例部署、高写入并发或大量用户库的集中运维，再评估 PostgreSQL、明确 owner_id 的数据模型和行级安全策略。更换数据库不能自动修复应用层越权。本次没有容量压测，不能给出可承载的在线人数。

## 判断

当前项目是一个本地优先的、多功能单体应用：React 前端、Express API、WebSocket、AI 编排、插件定时任务运行在同一套应用内，Electron 负责桌面包装。代码已经有一定安全基础，但还不能据此认为适合直接开放公网或分发当前安装包。

主要问题是三种边界没有统一落实：

1. **产品边界**：正式功能、实验面板、编辑工具、历史实现混在同一源码和发布流程里。
2. **安全边界**：HTTP 用户隔离已经存在，但文件备份、出站请求、WebSocket 会话和桌面网络暴露没有完全遵循同样的规则。
3. **代码边界**：目录已经分出插件，实际依赖和运行时职责仍高度集中，功能间还会直接访问彼此内部实现。

建议继续采用模块化单体，先修安全和发布边界，再逐步拆文件。现有规模没有显示必须立即引入微服务。

## 已有的安全基础

- 密码使用 bcrypt；有登录失败计数、账号锁定、邀请码和角色校验。
- JWT 有持久化随机 secret，并结合会话记录、token version 验证。
- HTTP 鉴权后按用户分配 `req.db`，业务库按用户独立保存。
- 已有 Helmet、认证/API 限流、公网模式 CORS 白名单。
- 普通图片上传有大小、类型和文件头检查，用户私有图片有鉴权读取路径。
- 角色和个人配置接口已对部分 API key 做脱敏。
- 后台队列已有全局并发控制及同 key 排队；部分后台循环会过滤不活跃/封禁用户。
- 管理员封禁、重置密码、强制退出等接口会主动关闭用户 WebSocket。

因此，重点应是补齐入口间的差异，而不是假设所有鉴权都要推倒重写。

## 发布前优先问题

这里的优先级按对外分发或多用户公网服务判断，不代表当前电脑已被攻击。

### 1. 发布产物带入本地管理员配置——发布阻断项

**证据**：根 `package.json:49` 的 `extraResources` 整体复制 `server`，过滤器没有排除 `.env`、`data.sqlite`、归档和测试目录。

在以下两个已有构建目录均确认存在 `resources/server/.env`，其中均有非空 `ADMIN_PASSWORD`：

- `release/win-unpacked/`
- `release-external-ui-final/win-unpacked/`

没有输出或写入报告任何真实密码。未检查压缩后的安装器，也未验证该值是否仍是实际账号当前密码。两个目录还包含 `server/data.sqlite`，但这个文件当前是 **0 字节**，不能将其描述成已确认的聊天数据泄露。

**处理**：采用发布文件白名单；模板与运行配置分离；打包后自动检查敏感文件与值。若这些构建曾对外发送，应更换其中仍在使用的凭据。

### 2. 本地模式实际监听全部网卡，桌面首次密码有固定回退值——高优先级

**证据**：`server/index.js:7581` 调用 `server.listen(PORT)`，没有指定 host。本次系统监听检查显示 8000 绑定 `::`，不是仅回环地址。防火墙和路由是否允许其他机器访问未测试。

`desktop/main.cjs:262` 将 `CP_PUBLIC_MODE` 设为 `0`，同时 `:266` 为 `ADMIN_PASSWORD` 提供写在源码里的固定回退密码。该密码仅影响没有认证库的首次初始化，不能推断现有账号一定使用它。

当前 `.env` 没有设置 `CP_PUBLIC_MODE`。对现有后端发送带测试 Origin 的未登录 GET 请求，返回了同样的 `Access-Control-Allow-Origin`；API 仍正确返回 401。宽松 CORS 本身不等于绕过鉴权，但与网络暴露、已知初始凭据组合后不符合本地产品的预期边界。

**处理**：本地/桌面模式明确绑定 `127.0.0.1`；公网模式显式开启并校验配置；首次凭据随机化或走安全初始化流程。

另：`docker-compose.yml:7` 的 `6333:6333`、`6334:6334` 未限定宿主机回环地址，也未配置 Qdrant API key。`config/qdrant.yaml` 的回环限制不能自动应用到未挂载该配置的容器。当前正在运行的本机 Qdrant 监听回环地址，不能把 Compose 风险说成当前 Qdrant 已公网暴露。

### 3. 备份功能绕过上传文件的用户隔离——多用户上线阻断项

**证据**：`server/plugins/backup/index.js:34` 支持旧 `/uploads/` 引用；`:64` 附近的路径解析只保证留在共享 uploads 目录，不保证属于当前用户。

从原文件提取纯路径函数进行隔离验证，当前用户为 `current-user` 时：

| 输入 | 函数结果 |
| --- | --- |
| `/api/media/uploads/mine.png` | 当前用户目录，符合预期 |
| `/uploads/users/other-user/private.png` | 其他用户目录，仍被接受 |
| `/uploads/` | 整个 uploads 根目录，仍被接受 |

用户可通过 `server/index.js:2487` 保存 avatar/banner；`server/db.js:2889` 的规范化没有对这些引用做归属校验。导出会按引用收集文件，而导入恢复流程 `backup/index.js:317`、`:364` 会按这些旧引用执行递归删除。由此存在越权打包其他用户文件，以及通过目录引用影响其他用户上传文件的代码路径。

这是纯函数验证与调用链检查，**没有对真实文件执行导出、删除或恢复**。读取他人具体文件仍需要知道或得到相关路径；根目录引用问题不应依赖路径保密来防护。

**处理**：文件操作强制限定当前用户根目录；只允许实际文件；禁止目录引用；历史公共上传资源单独迁移，不能继续信任可编辑 URL 作为删除目标。

附带问题：备份临时文件位于公开静态服务覆盖的 `uploads/temp` 中，当前 `/uploads` 中间件只拒绝 `users` 路径。知道文件 URL 时存在导入期间访问备份的风险；应迁到 Web 根目录之外。

### 4. 公网出站 URL 防护可绕过——多用户上线阻断项

**证据**：`server/httpGuards.js:28` 和 `server/plugins/mcpLab/inputGuards.js:45` 都用字符串前缀判断 IPv4 映射 IPv6 地址。

在 `CP_PUBLIC_MODE=1` 下直接调用现有校验函数：普通 `127.0.0.1` 被拒绝，但 IPv4 映射 IPv6 形式的同一地址被放行。原因是 WHATWG URL 将主机规范化为十六进制形式，原来的点分十进制前缀匹配失效。链路本地地址也出现同样情况。

模型代理会调用公共 guard。MCP 抓取另有一份重复实现，并且 `runFetchUrl`（`mcpLab/index.js:393`）没有像公共 guard 那样校验 DNS 解析结果；域名解析到内网也未在该层被阻止。

**影响**：已登录用户可能借服务器访问其内网服务。只是开启 `CP_PUBLIC_MODE` 不能补齐这个缺口。

**处理**：集中使用一个出站请求适配器，正确处理 IPv4/IPv6、DNS 解析与实际连接地址，限制重定向、超时和响应体积。验证仅调用校验函数，没有发出内网探测请求。

### 5. WebSocket 生命周期没有完全跟随会话——高优先级

**证据**：`server/index.js:2076` 中，同一个 socket 每次收到合法 auth 消息都会加入对应用户集合，但切换身份时不移出旧集合；关闭时只从最后的用户集合移除。

隔离模拟原回调得到：用两个模拟有效账号依次认证后，该 socket 同时在 A、B 两个集合；关闭后仍残留在 A 集合。此验证使用假的身份校验和事件对象，没有连接真实账号。

这不是“无需凭据即可读其他用户消息”的证明，但它破坏了一个连接只属于一个会话/用户的约束。

此外，普通退出、撤销单个会话和本人修改密码的 HTTP 处理（`:2314`、`:2335`、`:2345`）没有像管理员管理接口那样关闭对应 socket；已建立连接也未看到令牌到期复验。未认证连接没有显式认证期限；WS 亦没有显式设置适合业务的载荷/连接限额。

**处理**：一次认证、绑定 sessionId、统一撤销入口、到期关闭、认证超时、消息与连接限额。保留已经存在的管理员断连逻辑并合并实现。

插件也还没有形成独立边界：socialHousing 直接依赖 cityDb；city 直接依赖 mcpLab；入口向所有插件提供 JWT_SECRET、认证库和其他用户 DB 的获取方法。对于可信内置代码，这不自动构成漏洞，但说明不能把这些模块当作受权限约束的外部插件。

`docs/ARCHITECTURE.md` 已经提出按 routes、realtime、chat、memory、repositories 逐步拆分的方向，适合继续落实。city 已经抽出了部分 routes/services，可以沿已有拆分继续，避免另起一套相互竞争的结构。

## 建议的分区与实施顺序

先定义五个区域，不要求立刻搬动所有目录：

| 区域 | 内容 | 发布策略 |
| --- | --- | --- |
| 核心产品 | 账号、角色、私聊/群聊、记忆、设置、必要备份 | 默认发布、必须回归 |
| 可选正式功能 | 城市、住房、经济、调度、关系、像素玩法 | 明确依赖与开关，后端未启用则无对应任务/接口 |
| 实验和创作工具 | MCP 实验面板、行为树调试、场景/素材编辑、布局调试 | 默认关闭或独立工具构建；是否转正逐项决定 |
| 独立工具包 | memory-mcp、受控维护/迁移脚本 | 独立入口、文档、测试和发布流程 |
| 历史与生成物 | 旧入口、归档脚本、dist、release、日志、运行数据 | 归档与生成产物分开；不混入产品源码发布清单 |

实施顺序：

1. **先补安全边界**：发布配置泄露、监听/初始身份、备份文件归属、SSRF、WS 会话。针对这些问题增加有意义的隔离回归测试。
2. **再收紧发布流程**：建立打包白名单、自动检查产物、统一环境配置、确定实验功能清单；补关键依赖修复。
3. **再拆后端入口**：提取 app 装配、认证会话、文件服务、WS、路由组，保持现有 API 行为稳定。
4. **再拆业务与前端**：按 chat、memory、city 等拆服务；前端统一 API/WS 客户端，拆出编辑工具和应用窗口管理。
5. **最后考虑扩容**：如果要提供公共多用户服务，再评估独立 worker、持久化队列、存储配额、数据库迁移和恢复演练。本地桌面版可以继续使用 SQLite 和单进程结构。

清理 Git 时需要特别注意：758 个已跟踪文件中，有 **296 个位于 client/dist**、**6 个位于 server/public/uploads**，还有那个 0 字节 `server/data.sqlite`。`.gitignore` 已有相关规则，但不会自动停止跟踪历史已提交文件。要先区分需保留的公共素材与运行数据，再调整跟踪清单，不能直接清空目录。

当前测试集中在私聊版本、topic switch、记忆引用和独立 MCP smoke；未找到已跟踪的 CI 配置或覆盖上述安全边界的测试。当前新增的 client/test、server/test 尚在未跟踪工作区中，发布验证需要将必要测试纳入版本控制。
