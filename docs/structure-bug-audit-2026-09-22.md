## 已复现的缺陷

### 1. 一个标签页保存成功，会删掉另一个标签页的未保存恢复记录

位置：`client/src/features/city/scene/useBehaviorTreeSync.js:44–47`。

触发条件：同一浏览器打开两个标签页，编辑同一个场景；A 的保存请求尚未返回，B 的新修改保存失败；随后 A 保存成功。

两个实例共用 `${storageKey}.pending-sync`，每次保存成功都会无条件删除这个键。无头 Chromium 中用两个标签页挂载真实同步 hook、控制模拟服务端响应顺序，得到：

1. B 保存失败后，恢复记录中存在 B 的修改。
2. A 保存成功后，B 内存中仍有修改，但恢复记录已经变成 `null`。
3. 刷新 B 后，它加载 A 的服务器版本，B 的未保存修改丢失。

这不绕过服务端 revision 检查；问题发生在浏览器本地的恢复数据上。建议优先修复：恢复记录按编辑实例保存，并携带操作 ID；保存确认只能删除自己对应的记录，刷新时仍须能找回该实例的未提交数据。

### 2. 已领取的虚拟转账花掉之后，退款仍能全额退回，凭空增加余额

位置：`server/features/economy/repository.js:129–150`，尤其是扣回收款方余额时的 `Math.max(0, balance - amount)`。

在真实 repository 和内存 SQLite 上执行正常业务操作：

- 初始：用户 520，角色 A 200，角色 B 0，合计 720。
- A 转给用户 100，用户领取，然后把全部 620 转给 B，B 领取。
- 用户余额为 0 时，退还 A 的第一笔 100。
- 接口操作返回成功；A 恢复为 200，用户仍为 0，B 为 620，合计变成 **820**。

这是应用内虚拟余额错误。建议退款前检查已领取款项能否足额扣回，余额不足时拒绝操作；退款标记和双方余额变化必须在同一事务内完成。

### 3. 转账扣款、领取标记与余额更新缺少共同事务

位置：`server/features/economy/repository.js:43–58`、`83–94`。生产数据库装配和调用路由也没有为这些操作提供外层事务。

通过内存 SQLite 的触发器在指定写入处抛出异常，已复现两种不一致：

- 转账记录插入失败：用户余额从 520 扣到 420，但转账表没有对应记录。
- 领取时余额入账失败：转账已经标为“领取”，收款方余额没有增加；重试返回“已经领取过了”。

这里验证的是写入失败恢复，不是把单进程 SQLite 的同步函数误判为普通请求并发竞态。建议把余额、转账状态、必要关联记录纳入完整事务，并对中途失败补回归测试。

### 4. 导入角色存档停止主动消息计时器后，没有恢复

位置：`server/features/backup/http/post-data-characterId-import.js:33–34`，后续成功路径和失败路径均没有对应恢复；计时器实际在 `server/features/private-chat/scheduling.js:64–69` 被删除。

调用真实导入 handler 和真实计时器模块，以替身隔离存档、数据库及索引操作，观察到：导入前有 1 个待执行计时器；导入成功（200）或事务执行失败（500）后，都变成 0 个。

设置页面的导入处理 `client/src/features/settings/useCharacterConfiguration.js:204–207` 只刷新角色列表，不重新建立 WebSocket。该入口下，原本会主动发消息的角色会停止主动消息，直到其他操作重新安排计时器。聊天设置抽屉的成功导入会刷新整个页面，可能通过重新连接掩盖这一问题，但失败路径仍存在。

建议由角色导入服务统一负责暂停和恢复：失败时恢复原有调度，成功时按导入后的角色状态重新安排；不要依赖前端刷新页面来补齐生命周期。

## 剩余结构问题

### A. 主界面的模块接口仍过宽

`client/src/app/App.jsx:373` 给 `ApplicationView` 传入 **161 个属性**，同时包括 UI 组件、图标、私聊和群聊状态、桌面窗口状态及操作函数。`useApplicationState.js` 仍把多项业务状态合成一个扁平返回值。

这使得文件虽已分开，阅读一个功能时仍需要来回追踪总入口、状态集合和整个视图。建议让纯展示组件自行导入固定组件及图标，再按桌面窗口、会话、通知等职责收窄接口，逐步明确谁拥有状态和副作用。

### B. 城市后端仍有职责混合的大模块

当前实际行数（包含空行）：

| 文件 | 行数 | 混合的职责示例 |
| --- | ---: | --- |
| `server/features/city/runtime/conversation.js` | 1912 | 上下文缓存、提示词拼装、模型输出解析、行为文本处理、城市事件转私聊 |
| `server/features/city/runtime/operations.js` | 1728 | 状态效果、行为树输入与压缩、城市行动执行、任务评价和市长操作 |

问题不只是文件长：`conversation`、`operations` 仍不能直接说明某项业务规则该去哪里查。建议按“行为生成与解析”“城市状态与行动结算”“城市事件转私聊”等实际职责划分，明确每个模块的输入、输出和错误处理责任。

经济模块和存档模块此次暴露的问题，也说明下一步需要明确完整业务操作的事务与计时器责任；仅移动函数到新文件还不够。
